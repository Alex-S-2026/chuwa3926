# Conceptual Questions

## Q1. Three Pillars of Observability: What are the three pillars of observability, and what is the primary purpose of each?

The three pillars are **Metrics, Logs, and Traces**. A simple way to remember them is:
- **Metrics tell you "How much?"**
- **Logs tell you "What happened?"**
- **Traces tell you "Where did time go?"**

1. **Metrics**
   - **Purpose:** Fast, low-cost monitoring of system health over time.
   - **Mechanism:** Numeric time-series data (for example CPU usage, request rate, error rate, p95 latency) sampled and aggregated.
   - **Best for:** Alerting, SLO dashboards, trend analysis, capacity planning.
   - **Limitation:** Great for detecting a problem, weaker for explaining root cause.

2. **Logs**
   - **Purpose:** Detailed event-level evidence of system behavior.
   - **Mechanism:** Discrete records generated by code paths (info/warn/error), ideally with structured fields like `userId`, `requestId`, `service`, `errorCode`.
   - **Best for:** Debugging exact failures, audit/compliance, forensic analysis.
   - **Limitation:** High volume/noise if not managed; harder to see big trends compared to metrics.

3. **Traces**
   - **Purpose:** End-to-end visibility of one request across multiple services.
   - **Mechanism:** A request gets a trace ID; each service adds spans with timing and metadata.
   - **Best for:** Microservice latency debugging, dependency bottlenecks, cross-service failure paths.
   - **Limitation:** More complex setup and sampling strategy needed at scale.

**Interview takeaway:**  
Use metrics to know *that* something is wrong, traces to know *where* it is wrong, and logs to know *why* it is wrong.



## Q2. Metrics Data Types: Explain the four common metric types and give an example use case for each.

The four common metric types are **Counter, Gauge, Histogram, and Summary**.

1. **Counter**
   - **Definition:** A value that only goes up (or resets when process restarts).
   - **Use case:** Count total HTTP requests, total errors, total jobs processed.
   - **Example:** `http_requests_total{status="500"}`.
   - **Why useful:** Ideal for rates such as "errors per second" using `rate()` in Prometheus.

2. **Gauge**
   - **Definition:** A value that can go up and down.
   - **Use case:** Current memory usage, active connections, queue depth, temperature.
   - **Example:** `db_connections_active`.
   - **Why useful:** Represents current state at a moment in time.

3. **Histogram**
   - **Definition:** Observations are bucketed into ranges; also tracks count and sum.
   - **Use case:** Request latency distributions, payload size distributions.
   - **Example:** `http_request_duration_seconds_bucket`.
   - **Why useful:** Can aggregate across instances and calculate percentiles centrally (for example p95 via `histogram_quantile`).
   - **Trade-off:** Bucket design matters; poor buckets give poor visibility.

4. **Summary**
   - **Definition:** Client-side calculated quantiles (for example p50, p95) plus count/sum.
   - **Use case:** Local service latency percentiles when cross-instance aggregation is not required.
   - **Example:** `rpc_latency_seconds{quantile="0.95"}`.
   - **Why useful:** Direct percentile output without server-side quantile computation.
   - **Trade-off:** Quantiles from summaries are hard/impossible to aggregate correctly across many instances.

**Rule of thumb:**  
For distributed systems and Prometheus-style fleet aggregation, **Histogram is usually preferred over Summary**.




## Q3. Structured Logging: What is structured logging, and why is it preferred over unstructured (plain text) logging in production systems?

**Structured logging** means logs are emitted in a machine-readable format (usually JSON) with consistent key-value fields instead of free-form plain text.

Example:
- Unstructured: `"User login failed for id 42 from 10.0.0.8"`
- Structured: `{"event":"login_failed","userId":42,"ip":"10.0.0.8","service":"auth","requestId":"abc123","level":"warn"}`

Why it is preferred in production:

1. **Queryable at scale**
   - You can filter by fields (`service=auth AND userId=42`) instead of fragile text search.
   - This makes incident triage much faster.

2. **Reliable parsing**
   - Log pipelines (ELK, Datadog, Splunk, Loki) parse JSON predictably.
   - Plain text often breaks due to wording changes.

3. **Better correlation**
   - Shared IDs (`traceId`, `requestId`, `sessionId`) let you connect logs with traces and metrics.
   - This is critical for root-cause analysis in microservices.

4. **Stronger governance**
   - Easier to enforce schema, redact sensitive fields, and support compliance/audit needs.

5. **Supports automation**
   - Alert rules and anomaly detectors can trigger from specific fields, not regex guesses.

Trade-offs:
- Slightly larger payload size.
- Requires schema discipline (field naming/versioning).
- Needs team conventions to stay consistent.

**Interview framing:**  
Structured logging converts logs from "human notes" into "operational data products" that tools and engineers can both trust.




## Q4. Distributed Tracing Concepts: Explain the relationship between Trace, Span, and Context Propagation in distributed tracing

In distributed tracing, these three concepts form one chain:

1. **Trace**
   - A trace represents the **entire lifecycle of one request** across services.
   - It is identified by a unique **trace ID**.
   - Think of it as the full story of "checkout request #X" from API gateway to payment to database.

2. **Span**
   - A span is a **single unit of work** inside the trace (for example one HTTP call, DB query, cache lookup).
   - Spans have start/end time, metadata, status, and parent-child relationships.
   - All spans with the same trace ID combine into a timeline/tree.

3. **Context Propagation**
   - The mechanism that **passes tracing identifiers between process boundaries** (headers, message metadata).
   - Usually includes trace ID, span ID, and sampling flags (for example W3C `traceparent` header).
   - Without propagation, each service starts a new unrelated trace and you lose end-to-end visibility.

Relationship summary:
- **Trace = complete request graph**
- **Span = one node/operation in that graph**
- **Context propagation = glue that keeps nodes in the same graph across network hops**

Why it matters:
- Lets you pinpoint latency bottlenecks and failure origin in microservice chains.
- Enables causality analysis ("Service A call caused Service B timeout").

Trade-offs/challenges:
- Requires instrumentation consistency across languages/services.
- Missing propagation in even one hop creates blind spots.
- Sampling strategy must balance observability value vs telemetry cost.



## Q5. Prometheus Pull Model: Prometheus uses a "pull" model for collecting metrics. Explain how this works and what are its advantages and disadvantages compared to a "push" model.

How the **pull model** works in Prometheus:
1. Each application/service exposes a metrics endpoint (usually `/metrics` in Prometheus text format).
2. Prometheus server is configured with scrape targets and intervals.
3. On schedule (for example every 15s), Prometheus sends HTTP requests to each target and stores returned samples.

### Advantages of pull model

1. **Centralized control**
   - Scrape interval, timeout, relabeling, and auth are managed from Prometheus config.
   - Easier operational governance than configuring thousands of clients.

2. **Built-in health signal**
   - If Prometheus cannot scrape a target, that itself is observable (`up == 0`).
   - This gives immediate signal that exporter/target is unreachable.

3. **Service discovery friendly**
   - Prometheus can auto-discover dynamic targets (Kubernetes, EC2, Consul).
   - Good fit for cloud-native environments.

4. **Simpler client libraries**
   - Apps only expose endpoint; they do not manage delivery queues/retries to metrics backend.

### Disadvantages of pull model

1. **Harder for short-lived jobs**
   - A batch job may start and finish between scrape intervals.
   - Common solution: Pushgateway for ephemeral jobs.

2. **Network reachability requirement**
   - Prometheus must be able to reach targets; difficult across strict firewalls/NAT boundaries.

3. **Potential scrape overhead**
   - Large number of targets with frequent scraping can create network and CPU overhead.

### Compared to push model
- **Push model:** clients send metrics to backend.
  - **Pros:** Works well for ephemeral/offline clients; no need for backend to reach clients.
  - **Cons:** Harder centralized control and target liveness semantics; client complexity increases.

**Decision perspective:**  
Prometheus pull is excellent for long-running, discoverable services. Push is often chosen for edge devices, short-lived workloads, or constrained network topologies.
